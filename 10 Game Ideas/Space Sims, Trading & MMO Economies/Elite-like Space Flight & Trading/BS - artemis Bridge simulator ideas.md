## Business Model

“Community based, closed team development”

Early 2017 I will prototype the combat system and strategic layer in Love2d. This will be two separate prototypes demonstrating core gameplay concepts. These will be shows to parties I am interested in working with. Revisions to the game design can start and someone needs be volunteer to make all the Art Style choices. If there is no team at this point then I would not start this project.

May 2017. The first 6 month phase begins. During this phase the team works to complete a playable prototype of the multiplayer deathmatch part of the game (see below). There is no payment for work completed during this period, but 15% of future sales will be given out based on hours spent developing the prototype. During this time concept art is also being generated to be used for the kickstarter campaign. Core blocks will be reused during the next phase.

Nov 2017. The prototype is taken to Kickstarter with a goal of 80% the required budget to finish the full game. Here the original crew decides if they want to stay on or leave the project. Cash generated by this kickstarter is not considered as “sales” but will be used to fund features of Phase 2. Features of the full game will be given a “cost” which will be used to calculate the funding goal. Bloat features will be appraised and then added as stretch goals (to be revealed over time). 20% of Kickstarter funds are kept for the final bug fixing stretch.

Feb 2018. Assuming the Kickstarter is successful, work begins. Team members can take on feature blocks and are reimbursed in \$\$\$ when the feature is complete. Hours logged are also reimbursed with a share of 65% of the profit share. This is to promote working for as cheap as possible (upfront vs profit share). The final 20% of profit share is used for after release bug fixing and maintenance. This Phase should be scheduled so it takes no longer than 12 months, using the Frankfurt Indie dev meetup as milestone dates to get feedback on Playable versions. Monthly playable versions should be a group goal. As much time as possible should be saved by using the Unity Asset store.

Jan 2019. Final balancing and playtesting

Feb 2019. Release day for version 1.0. Bloat features to come after this.

## Description

A 3d game with 2d movement and gameplay where groups of players crew different stations of a space warship. Players interact with the game through the UI elements (mouse) and keyboard commands. Combat is slower paced, not relying on aiming or reflex skill, but instead making tactical choices and using team communication. The game will be built using Unity.

## Game Concepts

- Non-persistant upgrade cycles

- Combat not the goal but the obstacle

- Multiple players per avatar

- Procedural generation

- Multi-layer gameplay (tactical/strategic)

- Single variable Dynamic difficulty

## Phases

### Phase 1: 6 month pre-kickstarter

1.  Client UI - Menus, Settings, Join, Server Lobby.

2.  Dedicated Server

3.  Basic join functionality - joining client is added to a ship until the ships crew is full. Then it adds a new ship. UI elements: ship number and how full the ship is.

4.  PLAYABLE STATE: “technically playable” multiple players can log in and see the names of their crew and how many ships are in the game.

5.  Ship struct: UI elements for a ship divided amongst players. Ships have a list of UI elements and some sort of “profile” for each different amount of players. Ships also have a set of variables that get synced across the network. UI elements just modify values. UI is input and output. Ability for players to request position change (as in Battlefield)

6.  Ship damage system and combat system including movement and terrain. More on this later, I have two different designs.

7.  PLAYABLE STATE: “deathmatch” Crew are split between two identical ships that respawn randomly in a small area. The gameplay should be complex enough that more players crewing a ship make it more efficient and victorious. Tweak complexity until it feels good. This ship will become the main player ship and a benchmark for enjoyment (1, 2 and 3 player profiles for the ship UI).

## Combat System Prototypes

### Design Axioms

- The mechanics should support the ideal that a ship crewed by more players is more capable.

- A ship must be pilotable by a single player. I very highly skilled player could still defeat three very young players in another ship but not easily. Ideally he should WANT to have 1 extra newbie on his ship.

- Avoid the “committee effect”. This is where it would be better for all players to just do exactly as one player says, or even to let the one player just play for them (Arkham Horror, Battlestar Galactica).

- Combat is not the goal, but the obstacle to be dealt with as quickly as possible

- Complete Destruction of enemies is the LEAST effective way to deal with combat

- Defences should be active. Player input and reflexes should affect incoming damage as much as it affects outgoing damage.

- Attacks should not be simple HP buffer sinks. Dealing damage should require constant attention and tweaking to be successful.

- Damage should be boolean. Does this system work yes/no. No hitpoints!

- Ships should not be invincible (perma-tank)

- All crew should have something to do during combat (and something else to do outside of it)

- Some resources are shared amongst crew, some are per crew (but still allocated by the “captain”).

- Captain (most skilled player) is the helmsman in the early version, but the system must allow new players to try all roles.

### Prototype 1: Movement Example



The player can steer the ship left and right and adjust velocity using forward/back keys. There are three sliders on the screen which are changed using the number keys. There are also red zones around the player ship which indicated the best firing zones. The blue hexagon shows if the torpedo is ready to be fired.

The three sliders are linked, so that changing one modifies the other two in the opposite direction. The levels are set by pressing a number key corresponding to the slider and there are perhaps 10 positions on each slider. The actual value of the slider changes slowly to the desired value, half a second after buttons are no longer pressed. Sliders which are dropping drop at twice the speed of those that are increasing, meaning the ship is less powered in total while changing. A sound effect plays when the sliders begin moving.

These sliders represent Forward Thrust/Top Speed, Turn Rate and Weapon Power.

The camera stays fixed to the player ship. There are several objects flying around in different patterns for the player to destroy. Each requires the player to keep the laser firing until the shields go down, then press the alt-fire button to fire a torpedo to kill the target. The torpedo takes a long time to recharge, long enough that if the player launches it early, the enemy target will have time to turn its shields back on.

Lasers fire automatically at the closest target, but do not switch once they are firing. Firing can be toggled with spacebar.

Feedback of damage is shown as such: Red aura means you are not dealing enough damage to lower the shield, Yellow means the shield is being damaged. The gameplay promotes players to find the lowest possible damage score which affects the enemy shield.

### Prototype 2: Full damage system



This is a shooting range prototype and is considerably more complex that the previous one. The player will not move, nor will the target. The aim here is to demonstrate the full detailed shield/laser system. The image shows the player (green) and the target (blue). On the right is the simplified laser ui to select range and laser power, as well as to see how full the laser capacitor is, and if the torpedo is ready. The player must endure constant attacks as well, and manage his defences (to demonstrate the active defense component). It should be easier with two players.

The player of the prototype attempts to destroy the target and is then presented with a new one, at a different range, with a different shield configuration. The gameplay abstracts away all of the positional gameplay of actually flying around in space.

There are four UI areas on display. Left Top is Shield Management, Left Bottom is Missile Defence, Right Top is Laser Management and Right Bottom is Missile Launchers.

Along the bottom is a slider where the player can allocate more power to Defence or Offence.

Targets will have a variety of shield attributes:

- Damage threshold. Damage below this number per shield is ignored. Damage over this number begins the overload timer

- Full strength time. How long the shield will be 100% coherent

- Zero strength time. After how long will the shield fail automatically

- Number of shield points. This is how many concurrent beam hits the ship can endure.

- Shield capacitor. This fills up slowly over time. If it fills then all shield go down and must recharge. This is to stop ships being invincible.

- Recharge time. Starts when all shields are down, or when a shield is still active but has not been fired upon for a set time.

Lasers are applied to shields. The first countdown “Full strength” countdown is not affected by laser power so always takes the same time. The second one is affected by laser power, so can be dropped faster. Players need to change power settings correctly at the right time to efficiently damage enemies. Since shield drop is random after the initial overload timer, the attacker will not know exactly when the shield will drop.

Drop percent is very low, and is checked every frame. Generally the zero strength time will be much longer than the shield capacitor can last.

Shield capacitor fills at a constant and fixed rate while the shields are under fire. This must drain before the “shield recharge time” begins counting. This means that efficiently bringing down shields also gives you the smallest window to launch your torpedo.

Once shields drop the player must launch torpedoes to finish the target off. For the purposes of this prototype the player just presses a button to launch a torpedo and it takes a second to arrive.

Dropped shields take a long time to become active and cannot be renewed until all shields are dropped.

Lasers do not damage hulls at all.

#### Laser Control UI

The Laser screen shows three arcs, each with three range bands. Each of these 9 quadrants can be clicked to activate or deactivate them. The ranges take time to change when modified. They take longer to increase than to decrease. Each arc can be disabled as well, which increases the laser power in the remaining arcs.

This screen also shows 6 Laser emitter pips, which are always divided between the active arcs. These can be toggled individually. They are disabled instantly but they take several seconds to bring back online.

“Damage” or the speed at which the second shield threshold drops is based on the distance from the current arcs “optimal range” which is 80% of the current max range. This distance modifies the damage which is calculated from the Current Emitters in the arc that are active.

Lasers also have a capacitor which is drained while lasers are firing to stop them being fired forever on full power. This drains slower if emitters are firing in low range arcs. The amount of laser power being given modifies the recharge rate so with the correct settings the lasers can be fired forever.
